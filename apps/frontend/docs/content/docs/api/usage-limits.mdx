title: Usage Limits
description: Understand rate limits and quotas for the Reloop API.
---

Reloop enforces rate limits on API requests to ensure stability and fair usage.

For management endpoints (e.g., domain verification, contact management, configuration), rate limits are scoped and applied per **organization**.

### Default Endpoint Limits

| Endpoint / Operation | Limit | Window |
|----------------------|-------|--------|
| Domain Operations (create, delete, verify) | 10 requests | 60s |
| List Contacts | 60 requests | 60s |
| Create Channel | 30 requests | 60s |
| Update Preferences | 10 requests | 60s |
| Generate Token | 5 requests | 60s |

---

## Email Sending Limits

Email sending endpoints use a multi-layer rate limiting strategy:

| Layer | Limit | Window | Scope |
|-------|-------|--------|-------|
| IP | 20 requests | 60s | Client IP |
| User | 50 requests | 60s | Authenticated User |
| Organization | 100 requests | 60s | Organization |
| Organization Daily | 5,000 requests | 24h | Organization |
| Global | 500 requests | 60s | Infrastructure-wide |

---

## Rate Limit Headers

Every API response includes headers indicating your current rate limit status:

- `X-RateLimit-Limit` — Maximum requests allowed in the window.
- `X-RateLimit-Remaining` — Requests remaining in the current window.
- `X-RateLimit-Window` — Size of the window in seconds (management endpoints).
- `X-RateLimit-Reset` — Unix epoch timestamp when the window resets (email endpoints).
- `Retry-After` — Seconds to wait before retrying (returned with `429` responses).

### Example 429 Response

```json
{
  "message": "Too many requests",
  "why": "You have exceeded the limit of 10 requests per 60s window for this operation.",
  "fix": "Wait 42 second(s) before retrying.",
  "retryAfter": 42
}
```
