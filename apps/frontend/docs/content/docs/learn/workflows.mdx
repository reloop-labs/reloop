An **automation** sends emails for you when something happens in your app. You track a **trigger** (a custom event like `user.signed_up`) for a contact, and Reloop runs the automation's steps for them: send an email, wait, check a condition, and branch.

<Tabs>
  <Tab title="Desktop" icon="monitor">
    ## Create a trigger

    1. Go to [Automation → Triggers](https://reloop.sh/dashboard/automation/triggers)
    2. Click **Create Trigger**
    3. Name it (for example `User signed up`) and add the properties your app will send, such as `plan`
    4. Save, then copy its key from the row menu (**Copy key**)

    ## Build an automation

    1. Go to [Automation](https://reloop.sh/dashboard/automation)
    2. Click **Create Automation**
    3. Pick the trigger that starts it
    4. Add steps after it: **Send email**, **Delay** and **Condition**. A condition has a **Yes** and a **No** path
    5. Click **Publish** to start it

    After you edit an active automation, click **Publish changes** so new contacts get the new steps.

    ## Start it from your app

    The trigger's code drawer shows a ready-to-paste snippet with its key. You can also use the **Code** tab on this page.

    ## Pause an automation

    Open the automation and click **Pause automation**. It stops starting for new events, and contacts in progress are cancelled at their next step.

## Steps

| Type | Config | What it does |
|---|---|---|
| `trigger` | `{ eventName }` | Starts the automation. Every automation has exactly one. |
| `send_email` | `{ template: { id }, from?, subject? }` | Sends a [template](/docs/learn/templates) to the contact. Its From and subject come from the template; `from` and `subject` are used only when the template has none. |
| `delay` | `{ amount, unit }` | Waits before the next step. `unit` is `minutes`, `hours` or `days`. |
| `condition` | a rule or a group | Checks the contact or the event and takes the Yes or No path. |

Connections link steps by key: `{ from, to, type }`. `type` is `default` between steps. A condition has one `condition_met` (Yes) and one `condition_not_met` (No) connection.

## Conditions

A rule checks one field:

```json
{ "type": "rule", "field": "trigger.plan", "operator": "eq", "value": "pro" }
```

A group combines rules. With `and` every rule must match, and with `or` any rule can:

```json
{
  "type": "and",
  "rules": [
    { "type": "rule", "field": "trigger.plan", "operator": "eq", "value": "pro" },
    { "type": "rule", "field": "contact.company", "operator": "exists" }
  ]
}
```

| Field | Reads |
|---|---|
| `trigger.<name>` | A property sent with the event, e.g. `trigger.plan` |
| `contact.email`, `contact.firstName`, `contact.lastName`, `contact.status` | The contact |
| `contact.<name>` | A [contact property](/docs/learn/contacts/properties), e.g. `contact.company` |

| Operator | Matches when the field |
|---|---|
| `eq` / `neq` | equals / does not equal `value` |
| `contains`, `starts_with`, `ends_with` | contains, starts with, or ends with `value` |
| `gt`, `gte`, `lt`, `lte` | is a number greater than, at least, less than, or at most `value` |
| `exists` / `not_exists` | is set / is not set |
| `is_empty` | is not set or is blank (no `value` needed) |

Text comparisons ignore case. To compare against another field instead of a fixed value, pass `{ "var": "trigger.expected_plan" }` as `value`.

## How a contact moves through it

- **Once per automation.** A contact is enrolled in each automation once. Tracking the event again does not restart it.
- **Only subscribed contacts.** If the contact unsubscribes or is blocked, they leave the automation at their next step.
- **Pinned to a version.** Each enrollment finishes on the steps that were published when it started, even if you publish changes later.
- **Enrollment status.** `active` while it runs, then `completed`, `cancelled` (paused, deleted or unsubscribed) or `failed`.
