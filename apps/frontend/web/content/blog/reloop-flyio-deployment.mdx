**Run your app on Fly.io, and send its email through Reloop.** Fly is a great place for web apps and workers, but it's a poor place to run a mail server: you can't set reverse DNS (PTR) on Fly IPs, and most large mailbox providers penalize or reject mail from IPs without it. So set `RELOOP_API_KEY` with `fly secrets`, send over HTTPS or Reloop's SMTP relay, and let Reloop handle delivery. If you want to self-host Reloop itself, put it on a VPS next to your Fly apps.

This guide covers why, how to wire it up in a few minutes, and how to keep email off your request path with a Fly worker process.

---

## Why not send directly from a Fly machine?

It's tempting to run Postfix, or point Nodemailer straight at recipients' MX servers. Here's what Fly's own staff say about that on the [Fly community forum](https://community.fly.io/t/outbound-port-25-direct-to-mx-smtp-blocked-by-default-on-new-accounts/28537):

- There's no per-account block on outbound port 25.
- But direct-to-MX delivery needs reverse DNS on the sending IP, and Fly doesn't offer customer-configurable PTR records.
- A dedicated egress IP (`fly ips allocate-egress`) gives you a stable address, but still no PTR, which "most large receivers will penalize or outright reject."
- Their recommendation: relay outbound mail through a transactional email service.

Shared egress IPs make it worse. Anyone else's bad mail from the same IP range affects you, and users regularly report connections to Gmail and other providers timing out or being dropped.

| Approach | Reverse DNS | Reputation | Result |
|---|---|---|---|
| Direct SMTP from a Fly machine | Not configurable | Shared or brand new | [Spam folder](/blog/why-emails-land-in-spam-fix) or rejected |
| Dedicated Fly egress IP | Not configurable | Yours, but cold | Still penalized by large providers |
| Relay through Reloop | Handled | Warm, monitored | Inbox |

## What you need

1. An app running on Fly.io (`fly launch` in any project).
2. A Reloop API key from the [dashboard](https://reloop.sh/dashboard/api-keys). Keys start with `rl_`.
3. A verified sending domain in Reloop. See [connect a domain](/docs/guides/connect-domain). DNS for your domain lives wherever it does today; it doesn't need to move to Fly.

---

## 1. Store the API key as a Fly secret

```bash
fly secrets set RELOOP_API_KEY=rl_your_api_key_here
```

Fly encrypts the value and injects it as an environment variable into every machine in the app. Setting a secret triggers a rolling restart, so the new value is live as soon as the command finishes.

Never put the key in `fly.toml` under `[env]`. That section is plain text, committed to your repo.

## 2. Send over HTTPS (recommended)

The HTTP API is the simplest and most reliable option from a container: one HTTPS request on port 443, a JSON response with the email ID, and structured errors.

### Node.js

<InstallSdkCode />

```typescript
// src/lib/reloop.ts
import { Reloop } from "reloop-email";

export const reloop = new Reloop({ apiKey: process.env.RELOOP_API_KEY! });
```

```typescript
// anywhere on the server
import { reloop } from "./lib/reloop";

const { response, emailError } = await reloop.mail.send({
  from: "Acme <hello@mail.acme.com>",
  to: "user@example.com",
  subject: "Your login link",
  html: '<p><a href="https://app.acme.com/login?token=…">Sign in</a></p>',
  text: "Sign in: https://app.acme.com/login?token=…",
  tags: [{ name: "type", value: "magic-link" }],
});

if (emailError) {
  console.error(emailError.status, emailError.message);
}
```

The SDK returns `{ response, emailError }` instead of throwing, so a failed send never crashes a request handler. More patterns are in the [Node.js email guide](/blog/send-email-nodejs).

### Any language

It's one `POST`, so it works from Elixir, Go, [Python](/blog/send-email-python), Rails or anything else you deploy on Fly:

```bash
curl -X POST https://reloop.sh/api/mail/v1/send \
  -H "x-api-key: $RELOOP_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "from": "Acme <hello@mail.acme.com>",
    "to": "user@example.com",
    "subject": "Hello from Fly.io",
    "text": "Sent from a Fly machine through Reloop."
  }'
```

There are official SDKs for [Python, Go, Ruby, PHP, Rust, Elixir and Java](/sdk) as well.

## 3. Or use the SMTP relay

If your framework already sends through SMTP (Rails Action Mailer, Phoenix Swoosh, Django, Laravel), you don't need to change any code. Just change the settings:

| Setting | Value |
|---|---|
| Host | `smtp.reloop.sh` |
| Port | `587` (STARTTLS) |
| Username | Your Reloop API key |
| Password | Your Reloop API key |

Store them as secrets too:

```bash
fly secrets set SMTP_HOST=smtp.reloop.sh SMTP_PORT=587 \
  SMTP_USERNAME=rl_your_api_key_here SMTP_PASSWORD=rl_your_api_key_here
```

For example, in Rails:

```ruby
# config/environments/production.rb
config.action_mailer.delivery_method = :smtp
config.action_mailer.smtp_settings = {
  address: ENV.fetch("SMTP_HOST"),
  port: ENV.fetch("SMTP_PORT").to_i,
  user_name: ENV.fetch("SMTP_USERNAME"),
  password: ENV.fetch("SMTP_PASSWORD"),
  authentication: :plain,
  enable_starttls_auto: true,
}
```

You're connecting to a [relay on 587](/blog/smtp-ports-explained) with authentication, not delivering to recipients' MX on port 25, so the PTR problem above doesn't apply. Examples for other languages are in the [SMTP docs](/docs/examples/smtp/introduction).

## 4. Keep email off the request path with a worker process

Fly apps can run several process groups from one image. Use one for your web server and one for background jobs, and send email from the worker. A slow send never slows a page, and failed sends can be retried.

```toml
# fly.toml
app = "acme"

[processes]
  web = "node dist/server.js"
  worker = "node dist/worker.js"

[http_service]
  internal_port = 3000
  processes = ["web"]
```

```typescript
// src/worker.ts (sketch using any queue you already run, e.g. BullMQ on Redis)
import { Worker } from "bullmq";
import { reloop } from "./lib/reloop";

new Worker(
  "emails",
  async (job) => {
    const { emailError } = await reloop.mail.send(job.data);
    if (emailError && (emailError.status >= 500 || emailError.status === 429)) {
      throw emailError; // let the queue retry
    }
  },
  { connection: { url: process.env.REDIS_URL! } },
);
```

Then scale each group on its own:

```bash
fly scale count web=2 worker=1
```

If you can't use a queue but want retries to be safe, call the HTTP API with an [`Idempotency-Key`](/docs/api/idempotency) header. Reloop replays the original response for 24 hours instead of sending twice.

## 5. Receiving email

Fly apps can't receive mail on port 25 for the same reasons they can't send it well. Use Reloop's inbound instead:

1. Turn on receiving for your domain in Reloop and add the MX record it shows.
2. Create a webhook for the `email.received` event pointing at your Fly app, for example `https://acme.fly.dev/webhooks/reloop`.
3. Verify the `Reloop-Signature` header on each request. See [verifying webhooks](/docs/webhooks/verify-webhooks-requests).

Your Fly app gets a signed JSON event with the sender, subject, thread ID and more. The full message, including attachments, is available through the inbox API.

## Should I self-host Reloop on Fly.io?

We don't recommend it, and we don't ship a Fly configuration for it. Reloop's MTA needs to deliver directly to recipients on port 25 and receive on port 25, which runs straight into the PTR limitation. The stack is also a multi-service Docker Compose deployment (around 20 containers and about 22 GB of images), which doesn't map neatly onto Fly Machines.

If you want to run Reloop yourself, use a VPS from a provider that lets you set reverse DNS and open port 25:

| Option | Guide |
|---|---|
| One command on Ubuntu or Debian | [Deploy on VPS](/docs/self-host/vps) |
| Coolify | [Reloop on Coolify](/blog/reloop-coolify-setup) |
| Overview and trade-offs | [Self-hosted email infrastructure](/blog/self-hosted-email-infrastructure) |

Your apps can stay on Fly and point at your instance by setting the SDK's `baseUrl`, or `SMTP_HOST`, to your Reloop server.

## Checklist

- [ ] `RELOOP_API_KEY` set with `fly secrets set`, not in `fly.toml`
- [ ] Sending domain verified in Reloop (SPF, DKIM, DMARC)
- [ ] App sends through the HTTP API or `smtp.reloop.sh:587`, never direct-to-MX
- [ ] User-facing sends happen in a worker process or queue
- [ ] Inbound handled by Reloop with a signed `email.received` webhook
